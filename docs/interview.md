# Что уметь объяснить на собеседовании

Покажите четыре демо-цели и объясните, почему HTTP-ошибка, закрытый TCP-порт и превышение времени — разные результаты проверки.

1. **Горутина и поток — одно и то же?** Нет. Горутины планирует runtime Go; многие горутины могут выполняться на меньшем числе системных потоков. Здесь они позволяют ожидать несколько сетевых операций одновременно.
2. **Зачем канал заданий?** Он передаёт каждому работнику конкретную цель и её индекс. После закрытия канала работники завершают цикл.
3. **Почему недостаточно пула на каждый запрос?** Десять запросов по четыре работника могли бы открыть 40 соединений. Общий канал-семафор ограничивает совокупную сетевую параллельность.
4. **Зачем ограничивать число пакетов?** Даже ожидающие горутины и запросы занимают память. Отказ при перегрузке ограничивает рост работы в процессе.
5. **Почему нет гонки на массиве результатов?** У каждого задания уникальный индекс; читатель получает массив после ожидания всех работников. Общая статистика отдельно защищена mutex.
6. **Как действует context?** Отмена передаётся от входящего HTTP/gRPC-запроса до ожидания слота, HTTP-клиента или DialContext. Зависшие операции не должны удерживать ресурс после дедлайна.
7. **Почему важен defer cancel()?** Он освобождает ресурсы таймера. В цикле работников отмена вызывается сразу после отдельной проверки, чтобы не копить таймеры до выхода всей горутины.
8. **Где здесь TCP/IP и HTTP?** IP обеспечивает адресацию и доставку пакетов, TCP — надёжный поток байтов, HTTP — прикладной протокол. Успешное TCP-соединение ещё не означает корректный HTTP-ответ.
9. **Чем REST отличается от gRPC в проекте?** REST использует JSON и HTTP-маршруты; gRPC — сервисный контракт protobuf и сгенерированные типы. Они вызывают один Engine, поэтому правила совпадают.
10. **Почему клиенту нужен дедлайн gRPC?** Без него ожидание сбоя может длиться неопределённо долго. Сервер также задаёт верхнюю границу времени обработки.
11. **Почему нельзя отправить произвольный URL?** API проверяет только цели, заранее заданные владельцем. Это ограничивает направление исходящих сетевых обращений.
12. **Какие паттерны применены?** Worker Pool для параллельной работы; Strategy в виде функции Checker; адаптеры REST/gRPC вокруг одного движка. Интерфейсы вводятся там, где дают полезную заменяемость.
13. **Какова сложность выбора целей?** Справочник map строится за O(n), выбор k ID — в среднем O(k), массив результатов требует O(k) памяти. Сетевое время зависит от целей и лимита параллельности.

## Самостоятельные упражнения

- Добавьте демо-цель, возвращающую 404, и объясните результат.
- Сравните запуск с `-workers 1` и `-workers 4` на нескольких медленных целях.
- Напишите тест отмены запроса во время ожидания общего слота.
- Добавьте правило допустимых HTTP-кодов в конфигурацию, сохранив единое поведение REST/gRPC.
- Добавьте периодические проверки с корректной остановкой и тестом отсутствия утечек горутин.
